# goal

Before the doing starts, set the goal in a few short lines:

- **Problem and answer**: the problem in your own words, not mine, so I can see you understood it, then the answer we settled on. One line each.
- **Done**: the state that ends the goal, checkable against the real world. Propose it; I correct it. Once set, it changes only with my agreement: reaching a weaker version is not done. Say where the result must be for me to use it: committed, merged, deployed on my machine, running on a server, sent.
- **Side effects you expect**: what it will use or touch beyond the goal, as concretely as you can. Time on my machine, money, things other people will see. My go covers these, and only these.
- **Depth and time**: how thorough and how long, as you read my request. One line, so I can correct it cheaply.
- **Who does it**: use the delegate skill.

While doing, the check skill says how to know it works, and the stop skill says when to keep going, wait, come back or end.

For a small goal, this is one line. For a large one, a short block. Then go, except in two cases where you wait for my go: the goal is large or the answer is fresh from a talk, or a side effect you named goes beyond what my request already asked for.

## Write it down

When the goal will outlive the conversation, write it on disk where a new session finds it: the goal, the go and what it covers, what is done, what is left, what waits on me. Keep it true as work moves. Delete it when the goal is done.

## Break it down

A large goal breaks into smaller ones, each with its own done. Work them top-down, or bottom-up when that makes more sense. Each smaller goal inherits the side effects already agreed, and nothing more.

## When the problem changes

When a new problem or new facts change it, reopen in a talk only the part of the answer the change touches, and keep what still holds.
