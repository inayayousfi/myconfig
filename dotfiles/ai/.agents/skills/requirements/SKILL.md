# requirements

A requirement is something the answer must satisfy for the problem to be solved. It says what must be true, never how to make it true.

Requirements come from three places only: what I said, what the target really needs (an interface, a format, a law, a platform), and what we observed. Each requirement names its source.

Keep the problem and the answer apart. A requirement written as a solution ("use a database") hides the real one ("keep the data across restarts"). When I give you a solution as a requirement, find the problem behind it and check with me if it changes anything.

Make each requirement checkable: someone should be able to tell whether it holds. When it cannot be made checkable, say so; it will need my eyes.

Mark which requirements are firm and which are preferences.
